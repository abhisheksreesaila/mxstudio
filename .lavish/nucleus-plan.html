What to keep. What to correct.

Agree

The right boundaries

  • MAX owns inference. MX Studio owns model selection, lifecycle, readiness and observability.
  • One OpenAI-compatible entry point for satellite apps, with CLI and API as first-class clients.
  • Caddy for LAN HTTPS and mDNS for discoverability are reasonable optional additions.
  • LiteLLM is useful when per-app keys, provider policy, accounting or cloud routing are actual requirements.
  • systemd for a Linux appliance. A desktop/window manager is not a server dependency.
Correct before building

Five assumptions do not hold

  1. Apple GPU support under macOS does not establish MAX support on Apple Silicon Linux.
  2. Caddy's local CA is not automatically trusted by other devices.
  3. Custom progress JSON is not an OpenAI chat stream.
  4. Killing the active server on every model mismatch can interrupt other requests.
  5. LiteLLM virtual keys add PostgreSQL and admin lifecycle, not just YAML.
Hardware is the first gate, not the final deployment detail.

Assuming “Omachi” means Omarchy: treat it as an optional desktop choice. Asahi's current Fedora page advertises M1/M2 device support. Modular's current nightly docs describe evolving Apple GPU support through Metal on macOS, with a subset of model families manually exercised—not a verified M5 Ultra Linux appliance. The proposed 512 GB machine, exact OS support, available memory and performance remain unverified. Unified RAM is shared with the OS, activations and KV cache; it is not all usable model memory.

Recommendation: use a validated Linux + NVIDIA system for the reference MAX appliance. A Mac Mini on macOS can test the control plane and an explicitly validated CPU/Metal model path. Keep Apple-on-Linux as a separate research gate. Do not make a hardware purchase depend on this plan.

A small core, an optional gateway.

Recommended first slice

Local core

Client → Caddy → MX Studio → MAX

One installed, warmed default model. Static inference token from protected configuration. Caddy and discovery are enabled for LAN mode; loopback development needs neither.

Cost: no built-in virtual-key management or cloud failover. Avoids a proxy and database before the local workflow is reliable.

Gateway profile

Multi-app and hybrid

Client → Caddy → LiteLLM → MX Studio → MAX

LiteLLM adds per-app keys, model access policy and opted-in provider routing. PostgreSQL stores its key/accounting data.

Cost: another service, database backups/migrations, compatible timeout policy and more failure boundaries. If unique satellite keys are required on day one, include this profile immediately.

Existing ports are preserved: Studio 8080 and MAX 8100. Loopback binding is a proposed deployment change, not a claim about today's defaults. The existing CLI UI defaults to 0.0.0.0; MAX binding must also be configured and verified for the pinned version.

The controller contract matters more than the proxy.

1 / Standards-compliant inference, separate progress

Add POST /v1/chat/completions and GET /v1/models. Preserve OpenAI response envelopes, errors, stream chunks, final usage when supported, and [DONE]; support stream: false too. Do not reuse the existing browser-only /api/chat event format.

Resolve a public alias such as local-qwen to an approved installed HF ID and immutable serving configuration. The LiteLLM downstream provider prefix is openai/. Keep alias mapping and the model identity reported in responses consistent. Reject unknown models, unsupported request features, excessive context and disallowed architectures before admission; no arbitrary download, shell argument or custom-code execution from a chat request.

For Nucleus-aware apps, propose POST /api/nucleus/prepare returning a durable job ID, plus authenticated job status/events. Only advertise “compiling graph” or “loading weights” when the pinned runtime provides credible evidence; otherwise show “starting model,” elapsed time and readiness. Standard OpenAI clients cannot be assumed to display lifecycle events.

Initial policy: explicit prepare/prewarm. A not-ready chat gets an OpenAI-shaped 503 with Retry-After. Later, an opt-in request-triggered prepare may wait asynchronously for a bounded interval before headers. One prototype budget is 30 seconds for chat readiness and 10 minutes for the background start, configurable and validated against real models. Heartbeats do not defeat all client/gateway timeouts; no indefinite holds or fake token/status chunks.

2 / One lifecycle owner, request leases, fair admission

The serving identity is model + revision + device/quantization/serve configuration, not just an HF name. Track desired model, observed model, owned process identity, health, in-flight leases and transition generation. Persist useful recovery facts without treating a stale PID as proof of ownership.

State machine: stopped → starting → ready → draining → stopping → starting; failures become failed with reason and recovery action. A ready request holds a model lease until its stream closes. A switch blocks new admissions to the old model, drains active streams for a bounded grace period, terminates only the owned process group, waits for exit, then starts the next model. Never mark a new model ready because an unrelated process on the same port responds.

Use one controller worker and an inter-process ownership lock. In appliance mode, CLI/UI start/stop/prepare calls must submit to that owner, not instantiate a competing manager. Coalesce same-model preparation and use a bounded FIFO queue for model changes; later arrivals must not starve an already queued switch. Start with a pinned default model to avoid thrashing. Cancellation removes the request's waiter and closes its upstream stream; it must not cancel a shared start needed by another request.

Use existing MAX health semantics plus model identity verification; a 200 from /v1/models alone is insufficient. Check subprocess exit while polling, cap startup time, surface failure logs safely, and release resources on all exit paths. A startup failure leaves an honest failed/unavailable state; do not enter an automatic infinite reload loop.

3 / Trust, discovery, cloud policy and deployment

Trust: tls internal can issue a local certificate but clients must trust that CA through an explicit verified pairing/enrollment flow. Never disable TLS verification. For unmanaged clients, an owned DNS domain with DNS-01 issuance can avoid CA enrollment, but still needs a reachable LAN address, renewal connectivity and a suitable Caddy DNS provider module. Do not advertise public trust for .local.

Discovery: register _mxstudio._tcp.local., target port 443, the selected LAN IPv4/IPv6 addresses, and nonsecret TXT fields such as API path and protocol version. Publish/resolve the exact host used in the certificate; service discovery by itself does not make every hostname resolve. Prefer a conventional host label such as mxstudio.local over assuming api.mxstudio.local works everywhere. Unregister on shutdown and refresh after address/interface changes; avoid duplicate host ownership with Avahi. Never publish tokens.

mDNS is normally link-local: VLANs, multicast filtering and guest Wi-Fi can prevent discovery. Browsers do not generally offer raw mDNS browsing to pages; native satellite apps can implement it. Include a manual URL or pairing QR fallback. Discovery is neither authorization nor proof of server identity.

Cloud: local-only aliases never fall back to a cloud provider. Separate opt-in aliases have explicit per-key access, budgets, retries and eligible error classes. Do not fall back on authentication failures, invalid requests or every cold start. Never silently replay after partial output. Log routing decisions and timings, not prompts, responses or secrets by default.

Deployment: retain Pixi and the repository lockfile rather than the legacy modular install max bootstrap. Current upstream package naming has evolved; upgrade deliberately in a separate tested change if needed. Pin LiteLLM separately to prevent dependency conflicts. Use the packaged Caddy service where available, a controller service, optional LiteLLM and PostgreSQL services, protected credentials, persistent caches/state, cgroup cleanup, service hardening compatible with GPU access, and readiness checks beyond systemd ordering. MAX remains the controller's child—not an independently competing service.

Implementation plan, in dependency order.

Recommended scope: build the local core first, while retaining a clear gateway profile for the full original requirement. These are proposed changes—not commands or features that already exist.

00

Prove the target tuple

Record OS, exact chip/GPU, driver, MAX version, model revision, dtype, memory headroom and serving flags. Run a cold load, generation, warm request and a second start on the actual target.

Exit: saved load/generation evidence and latency/memory measurements. Choose a known supported Linux GPU profile, or explicitly label the Mac path experimental. Do not infer M5 Ultra readiness from a Mac Mini test.

01

Ship the local protocol slice

Extend servers.py for ownership and readiness; keep api.py thin with an additive inference router. Reuse registry.py, compat.py and existing jobs. Keep one installed default model warm. Add auth before any LAN exposure.

CLI proposal: pixi run mxs nucleus start, status and prepare <alias>. Use the same domain operations from CLI and API; a browser is optional.

Exit: ordinary OpenAI SDK streaming and nonstreaming calls succeed; existing Studio behavior remains intact.

02

Add reliable model transitions

Implement request leases, single-flight preparation, queue limits, transition generations, cancellation and crash recovery. Put blocking process work outside normal API request threads. Bridge preparation to durable jobs.

Exit: concurrent A/B requests never run against the wrong model, spawn competing servers or interrupt healthy streams during a normal drain. Optional bounded cold-start waiting follows this gate.

03

Make LAN onboarding honest

Add restricted Caddy config, a trust/pairing procedure, a discovery module and startup/shutdown integration. Keep management local or separately authenticated. Test actual certificate validation and resolution on a second device.

Exit: a native client discovers, verifies and authenticates; manual setup works without multicast. No public route exposes notebook execution or file operations.

04

Enable the optional gateway

Add litellm_config.yaml templates with environment references, PostgreSQL persistence, key creation/revocation, allowed-model policy and explicit cloud-capable routes. Coordinate queue, readiness and streaming timeouts across all hops.

Exit: unique app keys and revocation work after restart; a local-only request never reaches a cloud provider. Tests use mock providers; real cloud access requires approval and credentials.

05

Package and measure

Add a repeatable installer with a dry-run/preflight mode for one declared Linux distribution first. Detect ports/platforms, validate configs before enabling units, preserve edited files and existing state, document upgrades/uninstall, and retain logs on failure.

Add a deterministic editable notebook comparing cold load, warm TTFT, generation rate and swap cost, calling the real endpoint only when requested. Optional GUI progress should consume the same job schema.

Exit: reboot, upgrade and rollback are demonstrated; actual hardware results are stored. No hardcoded performance promises.

What this recommendation is based on.

Inspected repository evidence

  • docs/MXSTUDIO_ARCHITECTURE.md: domain ownership, one managed server, jobs and compatibility caveats.
  • notebooks/mxstudio/servers.py:47–140: existing start/stop, process group, persistent state, port 8100 and health check; macOS is currently forced to CPU. It does not contain request leasing or cross-process arbitration.
  • notebooks/mxstudio/api.py:394–469: installed-model checks and custom browser chat SSE—not a public OpenAI chat router.
  • notebooks/mxstudio/cli.py:242–245: Studio port 8080 and current all-interface default.
  • pixi.toml:1–18: current platforms are linux-64 and osx-arm64, not linux-aarch64; existing Modular dependency is not the latest upstream package layout.

The architecture guide contains older command wording; inspected source currently uses max serve --model. Treat executable behavior and the pinned version as authoritative. Existing unrelated worktree edits were left untouched.

Bottom line: build Nucleus as a deployment profile of MX Studio, not a second product/controller. Start with one warm model and an honest hardware claim. Add automatic swapping, LAN trust and virtual keys in tested layers.
